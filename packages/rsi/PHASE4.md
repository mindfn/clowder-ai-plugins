# RSI 插件第四阶段：被动观测（对齐稿，2026-11-19）

目标：插件除了主动实验，也能做被动观测。第一个用处是改进 clowder-ai 自己：项目是 clowder-ai，插件是观测能力，样本取自真实使用的记录。一个版本就是一次部署，比较部署前后的观测窗口。

- 被动观测和主动实验是 RSI 采证据的两种方式，共用一套评估项、七步准备、周期、成员和结论（FLOW §0）。插件到现在只做了实验型。
- 这一阶段只补被动型，实验型不动。

## 两种方式哪里不一样

| | 实验型（已有） | 被动型（要补） |
|---|---|---|
| 项目 | 本机能跑命令的代码仓库 | clowder-ai 本身，在日常使用里运行 |
| 准备第 3 步 | 登记执行器，插件试跑一次 | 选观测来源，插件拿已有记录试算一次 |
| 准备第 5 步 | 组 × 种子的周期计划 | 观测窗口、触发、最少样本 |
| 触发 | 每晚时段 | 样本数 / 天数 / 计数器（高置信反例） |
| 应用 | 这晚按计划跑各组 | 上次治理的改动部署上去，新版本生效 |
| 采集 | 各组 × 各种子的运行 | 窗口里的真实记录 |
| 评估 | 同晚对照 | 部署前后两个窗口比；没有同晚对照，归因多半只到「整体」 |
| 治理 | 方向 → 出版本 → 下一周期对照 | 方向 → 改代码 → 部署 → 下一个窗口 |

页面原型已经画了被动型（演示数据里 Clowder 的评估项），插件 console 也搬过来了，只是数据一直是演示的。要补的是后端。

## Host 现在给得了什么（2026-11-19 核对 develop_base c49962fca4）

**插件能读的**
- 你名下所有 thread 和消息历史：`threads.list`、`threads.readMessages`，往前翻页，每页最多 500 条。每条消息带 mentions、replyTo 和触发它的消息，回复还带执行状态和起止时间。
- 所有任务（`tasks.list`）、成员列表，以及插件自己的存储和数据目录。
- 订阅只能逐个 thread 订，能收到消息和执行状态。执行状态只有 started / catching_up / blocked / settled：
  - 不带 catId；
  - started 永远没有 replyTo（见「前置」）；
  - 没有 ended，也不补发。

**插件读不到的**
- 调用记录（模型、token、工具、报错）、路由和队列台账、session 和 digest、记忆、调度器、别的插件的数据。
- 不能按时间段跨 thread 读，也不能一次订阅全部 thread。
- 没有「观测来源」这种贡献类型，manifest 也没有权限可以申请。要多读，就得改 Host。

**F257 不在运行中的 Host 里。** 原型里 Clowder 那套评估项（身份真实性、路由目标送达、回合球权闭合……）抄自 F257 分支 `feat/f257-upstream-refresh` 的登记表（ec9f9a75，10-09）。这个分支是刻意没合的，PR #1462 一直保持 draft。就算在那个分支上，指标的判定规则也只是写给评估猫的文字。Host 里没有任何代码在算「明示目标与实际送达不一致次数」或送达率。

**F311 在 Host 里，但插件接不上。** 它是「改进 X」Program 的控制面：
- 只存引用。数字来自 owner 写进 git 的 YAML，目前一份都没有。
- 自动评估已经退役，只能手动开轮，每周一轮。
- 没有按样本数、天数、计数器的触发。
- 版本类型里没有「部署」。
- 适配器写死了两个，插件没有接入点。

所以被动型的采集只能由插件自己做，从上面能读到的记录里算。归因照 FLOW §6 沿用 F311 的结构（四层；能归因 / 说不清 / 证据不足 / 不可比），但不接 F311 的运行时。

## 第一批：观测 RSI 自己每晚的记录

为什么先做这个：
- 数据全在插件自己的存储里，不用等 Host。
- 量的正是 PHASE3 的目标「一个评估项一晚能连续推进多轮」。
- niuma、算术这些真实评估项每晚都在产生样本；今晚就有两个评估项共用调度。

**样本**：一个评估项的一晚，从时段开到关。夜间总结已经按晚把这些记录聚在一起（`nightDue`：时段里的周期、夜里自己定的决定、修复），样本也从这份记录里取，和总结卡对得上。

**量尺 E1（草案）**

| 量尺 | 方向 | 怎么算 |
|---|---|---|
| 每晚推进的周期数（主指标） | 越多越好 | 在时段里开始、并在时段里出了结论的周期数 |
| 等人 | 越少越好 | 时段里停下来等人的次数和总时长：结论等你定、等出版本、等确认 |
| 自动修复 | 只记 | 修复环接手的失败数、修好的数、转给评估的数 |
| 卡住（护栏，必须为 0） | — | 一个周期在跑、评估或等分析的状态里超过 2 小时没有新事件 |
| 空转（护栏） | 越少越好 | 夜里照旧重跑同一个版本、计划里没有新东西的周期数（GAPS「照旧 churn」） |
| 轮流（护栏，每晚一个值） | 越小越好 | 同一晚几个评估项推进的周期数，最多和最少差几个（今天修的饿死） |
| 叫醒成员 | 越少越好 | 每个周期叫醒成员的次数 |

**版本 = 插件装上的版本**：插件每次启动记一条部署（版本号、时间），窗口从这次部署算到下一次。只重启、没换版本的，算同一个版本接着往下，那一晚标「被重启打断」。

**比较**：拿上一个版本最近 N 晚和这个版本头 N 晚比，按晚取值，给区间。两边观测条件不一样时（当晚有几个评估项、换了成员、项目本身不同），照 F311 标「说不清」或「不可比」，不硬比。

**触发**：新版本攒够 N 个有活的晚上（建议 N = 3）。出现一个高置信反例（卡住、饿死）就立刻评估，不等满 N 晚。

**治理**：方向 → 治理执行成员改插件、提交 → 装上就是新版本 → 开新窗口。

## 第二批：从消息记录里算 clowder-ai 的行为

插件能读所有 thread 的消息，下面几项可以近似算出来：
- 行首 @ 了谁，被 @ 的猫有没有在同一 thread 里回。这近似「明示目标与实际送达」；路由台账读不到，所以只能是近似。
- 回复的执行状态是失败或空回复的次数。走查里小狸遇到过 empty_response。
- 行首 @lang 的次数，以及等了多久才回。对应「不必要升级」和等人。

代价：
- 每晚要翻全部 thread，得记住读到了哪儿，存储又会涨，要等分块存储。
- 这里的版本是 Host 的一次部署（合 develop_base、你重启）。插件只知道「重启了」，启动时不知道 Host 跑的是哪个提交。这一条要 Host 补：启动时把 Host 版本告诉插件。

## 第三批（要改 Host，这阶段不做）

调用记录、路由台账、session 只有 Host 有。要观测这些，有两条路：
- Host 给插件开只读的、按时间段的查询；
- 或者把 F257 的采集层（TraceEpisode、routingFact）合进来，再开给插件。

这是设计仓库的事，先记在 GAPS。

## 和实验型共用一套

- 同一个评估项记录、同一套成员、同一组工具（`rsi.task` / `rsi.conclude` / `rsi.propose` / `rsi.version`）、结论卡、方向、资料库、版本树和夜间总结。
- 不一样的只有下面几处：
  - 第 3 步登记的是观测来源，没有执行器。第一批的来源是内置的「RSI 记录」。
  - 第 5 步定的是窗口和触发，没有组和种子。
  - 一个周期就是对一个观测窗口的评估，没有 runs。
  - `rsi.task.evaluate` 给的是前后两个窗口的逐晚值和区间，不是同周期对照。

## 前置

1. **分块存储（PHASE3 第 7 项）**：被动观测每晚都要加记录。状态现在 840 KB，上限 1 MiB。
2. **Host：started 事件带上 replyTo。**
   - 根因：`messaging/lifecycle-delivery.ts` 通过 `lifecycleTriggerMessageId`（`index.ts` 5722 行）到 `InvocationRegistry` 里查。传进去的却是队列记录的 id，而且查的时候那条记录还没建好。队列记录本身带 `userMessageId`，用它就能对上。
   - 不修也能做第一批：卡住按「最后一个事件到现在多久」判。修了才能知道成员一轮结束却什么都没交。

## 不做

- 不动实验型，也不把实验型改成被动型。
- 不在插件里重做一套 F257 的采集层。Host 侧的采集该在 Host 做，插件来读。
- 不再拿模拟测试台当指标。self 评估项那条路，测的是冻结的旧版本和我们造的场景。测试台留作装新版本之前的回归检查，今天的饿死修复就是用它确认的。
