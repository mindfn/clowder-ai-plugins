# RSI (Capability Evolution)

The installed `official.rsi` plugin registers a native MCP server (`rsi-native`) with eight strongly typed tools:

- `rsi_task` — Claim your current turn and read the objective, project path, active step(s), dependency versions, or evaluation/discussion/version context.
- `rsi_submit` — Submit an initialization step (`"1"`–`"7"` or `goal`/`scope`/`run`/`rules`/`design`/`feedback`/`baseline`).
- `rsi_executor` — Register local execution commands (`preflight`, `submit`, `collect`, plus optional `get`/`cancel`/`analyze`/`resultMap`/`failureField`/`timeout`/`poll`) during Step 3.
- `rsi_conclude` — Submit a cycle evaluation (`cycle`, `verdict`, `findings`, optional `disposition: "advance" | "dead_end"`, optional `tag` (≤32 chars), optional `options` / `comparisons`).
- `rsi_propose` — Submit direction proposals during cycle discussion (`cycle`, `options`).
- `rsi_version` — Deliver a new version or execution repair (`change`, optional `commit`, optional `baseVersion`, `config` or `configPath`, optional `hypothesisId` / `scenario` / `tier` / `seeds` / `order` (`"grouped" | "interleaved" | "balanced"`) / `reservedSeeds` / `skipControl`, optional `aspects` (`["object" | "observability" | "rubric"]`), optional `changes`; or `cannot` when a repair or direction request cannot be satisfied). When `commit` is provided without `baseVersion`, the plugin derives `parent` from the nearest registered git-ancestor version automatically.
- `rsi_status` — Pure read-only inspection (`{}` inside an objective thread, `{ objectiveId, cycle?, scope?: "brief" | "full", sinceVersion?, versionsLimit? }` cross-thread, or `{}` outside an objective thread to list real objectives). Prefer `scope: "brief"` or `sinceVersion` for routine polling to keep context slim. Never open a browser just to inspect RSI state.
- `rsi_operate` — Delegated operator control (`hypothesis`, `abortCycle`, `expDecide`, `promote`, `requireCycleVars`, `cycleVars`, `prepConfirm`, `initStepRefresh`, `initRetry`, `stepMember`, `life`, `runCycle`, `evalAgain`, `discussAgain`, `versionAgain`, `lineageFix`), strictly gated to the owner-designated `policy.manager`. Cannot modify `policy.manager`, stop conditions, or delete objectives.

## Core Rules

1. **Always use the native MCP tools directly (match by tool suffix).** Different CLIs prepend their own server prefix to `rsi-native` (for example `mcp__plugin_official_rsi_rsi-native__rsi_task` on Kimi, `mcp__plugin__official_rsi__rsi_native__rsi_task` on Codex, or server `p_rsi-nati_*` on Antigravity). Match whichever tool in your tool list ends with `rsi_task`, `rsi_submit`, `rsi_executor`, `rsi_conclude`, `rsi_propose`, or `rsi_version`. The Host automatically authenticates your `catId` and `threadId` from request headers—never pass identity fields manually, and never read credential files or hand-call Host HTTP routes.
2. **Always call `rsi_task({})` first** on every woken turn so the plugin binds your turn to the current dependency versions.
3. **Keep `rsi_submit` JSON flat (2–3 levels):**
   - Pass `step` as `"1"`–`"7"` (or section name).
   - Pass `items` as `[{ id, title?, value, facts?: ["依据：README"], rec?, can?, tag? }]` — prefer flat string entries in `facts` (avoid deep nested objects).
   - You may also use the 2-level `values` shorthand on any step (including steps with newly created items): `{ step: "2", values: { "<id or title>": "<value>" }, unknowns: ["..."], next: ["..."] }`.
   - Pass `unknowns` and `next` as arrays of concise, self-contained bullet points so the console renders them as structured cards.
4. **Stage-specific payloads:**
   - **Step 3 (`run`)**: register commands with `rsi_executor` (preflight runs automatically) and submit `window` + Step 3 items with `rsi_submit`. Commands run with `cwd` set to each group's read-only version worktree; when Step 3's harness evolves ahead of an older `currentVersion`, prefix harness scripts with `{harness}` (the cycle's target version worktree, or the latest committed version during Step 3 preflight) and pass `{version}` / `{commit}` if needed so the upgraded harness can drive the untouched legacy control worktree in `confirm` cycles. **Contract**: `{harness}` is ONLY for locating measurement/harness scripts; the system under test MUST be read/deployed from `cwd` (or by `{version}` / `{commit}`), NEVER relative to the script's own path (e.g. `$(dirname "$0")/..`), otherwise control runs will silently deploy the new version and invalidate the comparison. Each run records both `env.commit` (code under test) and `env.harness = { version, commit }` (harness scripts used). For async remote jobs (`get` + `cancel` with `{job}`), make `get` emit a terminal JSON state (e.g. `{"state":"cancelled"}`) for unknown/already-cleaned jobs and make `cancel` exit 0 idempotently when already stopped so orphan-job guards clear cleanly. For deterministic non-environment rejections (config validation errors, precision/correctness gate rejections), emit `{"retryable":false,"reason":"..."}` (or `errorKind: "real"`) on `get`/`submit` output so the plugin records it as experimental evidence without wasting an env retry.
   - **Step 4 (`rules`)**: include `metrics: { version, items, slices? }` with one primary metric and finite numeric `threshold` on every guardrail. When an objective evaluates across operating points or slices (e.g., load/concurrency levels, dataset splits, sequence lengths, or scenarios), declare optional `slices: [{ id, name, axis, axisUnit?, stats: [{ id, name, unit?, dir: "up"|"down", threshold?, primary? }] }]` and emit matching `slices: { "<id>": [{ at, values: { "<stat>": number }, pass? }] }` from `collect` — the plugin then automatically aggregates across seeds, checks per-slice thresholds, renders the user-adjustable comparison table in the console, and generates the concise Markdown table + rolled-up guardrail summary in the chat conclusion card (so `findings` can stay focused on root cause and next steps instead of hand-formatted tables).
   - **Step 5 (`design`) / Step 7 (`baseline`)**: include `upcoming: { groups, seeds, order? }`. Optional `order` controls persisted queue order: `"grouped"` (default, group-first `AAAA / BBBB`), `"interleaved"` (per-seed `AB / AB`), or `"balanced"` (per-seed counterbalanced `AB / BA / AB / BA`, alternating group order on odd seed indices to mitigate thermal/time drift while keeping per-arm timeout, `{harness}`/`cwd` binding, and restart-safe resume). For multi-group `"interleaved"` or `"balanced"` cycles, the Host projects the persisted queue into every arm's `config.json` (including read-only control) as `pairedPlan: [{ group, seed }, ...]` (and strips spoofed `pairedPlan` otherwise).
   - **Evaluation (`rsi_conclude`)**: when a candidate branch is clearly falsified / retired (even in an `explore` tier where `verdict` is `tune` or `insufficient`), pass `disposition: "dead_end"` and a concise `tag` (≤32 chars) so the lineage overview marks the dead branch explicitly without altering nightly policy state machines.
   - **Governance / Repair (`rsi_version`)**: edit and commit in an isolated git worktree/branch (never mutate the user's dirty working tree), pass `aspects` (`["object"]`, `["observability"]`, `["rubric"]`, or combinations) honestly, pass `config` (object) or `configPath` (project-relative JSON path), and optionally pass `baseVersion` if branching back from a non-current version without a git commit.

## Cycle progress and cancellation

`rsi_status.active` and `rsi_task.progress` project the same readiness used by commands and scheduling: `phase`, `role`, `memberIds`, `canRunCycle`, `canSchedule`, `blockers`, and `nextAction`. Schedule-only blockers (window, window limit, explicit start, repeated automatic resume) do not prohibit an explicit manual run. Interrupted cycles resume their frozen plan rather than requesting new cycleVars. Preparation gaps distinguish `prepStale` (owner `initRedo` in Console), `prepInterrupted` (`initRetry` with `nextAction.section`), `prepConfirm` (`prepConfirm`), and `prepWorking` (wait); `prepPending` identifies a step that needs assignment or retry. An explicit decision releases the next cycle even if earlier analyst replies are still pending.

The owner or delegated manager may use `rsi_operate({op:"abortCycle", objectiveId, reason, note?})` while a cycle is running. `reason` is `budget`, `env`, `eliminated`, or `manual`; `note` is at most 240 characters. The response acknowledges durable cancellation intent (`aborting`); read status until cleanup settles. For async executors, an in-flight submit may finish acknowledging its job before cancellation; its existing submit timeout still applies; only submissions without any timeout get a 30-second abort grace ceiling. A missing acknowledgement is recorded as unconfirmed cleanup. Completed evidence (including experimental failures marked `evidence: true`) remains, remaining runs become `cancelled`, and each attempted cleanup records `cancelResult`. Failure retains the remote job ID for inspection and the existing orphan-job check. The objective is paused and never automatically starts another cycle. Non-environment aborts with valid completed evidence request a partial evaluation; this evidence never automatically confirms/promotes a candidate. Environment aborts or cycles without completed evidence do not wake an evaluator. Repeating abort when no cycle is running returns 409.


## Hypotheses and tiered experiments (alpha.138)

Use `rsi_operate(op="hypothesis", title, scenarios?, budget?, note?)` as the designated manager to create a hypothesis; pass `hypothesisId` to edit it or `archived: true/false` to archive/restore. Console owners have the same actions. Budget fields are `cards`, `minutes`, `cardHours`. IDs and source attribution are assigned by the plugin. Conclusions automatically collect `code`, `variable`, `discriminate` directions once per source cycle/member/direction; maintenance directions stay outside the pool.

Step 5 contains the **experiment specification**, separate from the hypothesis pool. Submit `specification: { tiers, scenarios? }` with `rsi_submit(step=5, ..., upcoming)`:

```json
{"tiers":[
  {"id":"screen","label":"Small-card screening","requireControl":false,"seedPolicy":"fixed","requireCycleVars":false,"resourceVars":["lease","cards"]},
  {"id":"full","label":"Full-system confirmation","requireControl":true,"seedPolicy":"fresh","requireCycleVars":true,"resourceVars":["lease","cards"],"promoteFrom":"screen","promotion":{"verdicts":["keep","tune"],"minCycles":1,"sameScenario":true}}
],"scenarios":["mixed","long"]}
```

Each higher tier refers to an earlier `promoteFrom`. `promotion` defaults to one completed cycle with verdict `keep`, `tune`, or `baseline`; `sameScenario` defaults to true (set false explicitly when scaling requires a different scenario). The last tier is the adoption tier and must require control and fresh seeds. Without `specification`, legacy explore/confirm behavior is unchanged; no records are migrated.

Plans accept `tier`, `scenario`, `hypothesisIds`. `rsi_version(hypothesisId?, scenario?, tier?, ...)` inherits the chosen direction's hypothesis unless explicitly specified. To advance an existing tested version, the prepare member updates Step 5's `upcoming` using that **same version and variables**, selecting the higher tier and hypothesis IDs; complete/confirm the dependent preparation as usual. A different code version must be screened again. Read `rsi_status.active.blockers` for missing evidence. Readiness requires completed lower-tier runs for the same hypotheses, tested versions/variables and metric definition; environmental failures, aborted/partial runs, failed guardrails and dead ends never qualify. Missing historical associations do not count as evidence. A source tier must match its frozen behavioral rule: renaming a tier preserves evidence, but tightening its requirements requires new validation.

Evidence belongs to candidate arms, never controls. With a control, only arms that meet the plugin's per-arm comparison criterion qualify; a `keep` for one candidate does not qualify another. Without control, only a single-candidate screen can use the whole-cycle verdict (split multi-candidate screens or add a control). Declared scalar and slice guardrails must pass for every arm/seed; missing slice tables, levels observed in other runs, or required values block advancement and adoption. Configured ladders apply slice guards to automatic confirmation too.

Only configured ladders save `parameters`: fixed-size SHA-256 fingerprints of the config definition, scientific overrides, resolved effective config and actual checkout revision (Git HEAD plus tracked edits), measurement harness revision and executor commands/result mapping. No config/base values are copied into run storage; legacy runs keep their existing footprint. Readiness checks the declared input identity. Immediately before submit, file contents are resolved from disk and the actual effective config/checkout fingerprints must match the qualifying lower-tier or selected-candidate evidence. A changed file or live checkout therefore cannot submit a candidate merely because its plan and declared commit stayed the same. Each submission retains a hashed execution context artifact alongside its config: cwd, placeholder values, commands, result mapping and timeout. Async recovery reuses those original inputs, never rewrites config from current version files, and checks the artifact/config hashes and tracked checkout identities before collection. Missing or changed original inputs (including older jobs without a retained context) cannot produce qualifying evidence. Evidence mismatch cancels queued runs, pauses the objective and requires an explicit Step 5 rescreen plan; it never triggers environment retries or direct repair/adoption. Unconfirmed remote jobs retain their job IDs and must be cleared using their original cleanup contract before another submission.

At conclusion, both cycles' actual run fingerprints must match, and **the current conclusion** must be positive and not `dead_end`, with complete evidence and passing guards. Missing fingerprints never qualify under a custom ladder. Seed/tier/paired-plan protocol fields may change. Optional `resourceVars` explicitly names resource/topology parameters such as lease IDs or card counts that may change; linked tiers must declare the same classification. This is project-authored, not inferred from names: do not list scientific workload parameters. Changing a source declaration invalidates its old evidence. Hypothesis status “Meets criterion” includes noninferiority and does not claim measured improvement.

Cycle starts freeze `tierRule`, tier/scenario/hypothesis associations and metrics. Only adoption-tier runs enter the existing winner/confirmation flow. `promote` for an active candidate under a configured ladder additionally requires highest-tier evidence; switching back to an already confirmed version retains its historical authorization. No automatic tier escalation or resource reservation is implied. `cycleVars` still requires an owner/manager binding; preparation cannot grant it. Historical versions/cycles missing associations display Unlinked.

### Cleanup after lost execution inputs

Cleanup is independent from scientific evidence eligibility. Each run retains its original `get`/`cancel`, cwd revision (Git HEAD plus tracked edits), placeholder values and bounded input hashes in state. Every live poll and cleanup invocation validates these inputs before execution and again before accepting its response. Changed or missing Git identity cannot acknowledge the original job as terminal. This same check governs normal polling, abort, plugin stop, window hold and orphan cleanup; only a trusted terminal query, successful trusted cancellation, or the explicit audited external confirmation may release a job ID. Non-Git projects have no Git revision check; their declared config/harness inputs still follow the checks below. A cleanup command using `{config}` must match the submitted config hash; one using `{harness}` must match the recorded harness revision. Commands must declare routing inputs through their placeholders, not read mutable global configuration implicitly. A command using only the original cwd/job ID remains available even when `execution.json` is missing. Unknown or damaged required inputs leave the job ID unresolved and block new submissions; they never count as successful cancellation.

If those inputs cannot be recovered, use the owner action `confirmCleanup` (with `objective`) or the designated manager tool **after externally verifying the original remote job has ended or been cleaned up**: `rsi_operate({op:"confirmCleanup", objectiveId, n, runId, jobId, note})`. The objective must be paused, the run stopped, the job ID must match exactly, and `note` must contain the external receipt or verification basis (1–240 characters). This records actor/time/original job/receipt and clears only that tracking ID; it does not resume execution, change evidence, or adopt a version. Submit the explicit rescreen plan and resume separately.
