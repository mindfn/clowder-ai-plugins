## Console

Host round 4 (fork `fix/pdl-console-round4`, upstream #1982) closed the console gaps below; alpha.17 uses it and needs that Host (it is not installed on a Host without round 4). The running page (develop_base `3071e45b93`) still has the three Host problems at the end of this list.

- **Reread flash and narrow loading (Host fixed).** A source that already has a value keeps it while it is reread, so a write or a selection no longer redraws the page as a skeleton; `.page` fills a column flex, so the loading state of a page view is full width in the panel.
- **Panel width and back (alpha.11, alpha.17).** `rsi.panel` is the same split as `rsi.home`; a split collapses in a panel that is not widened. Selection is plugin state (`plugSet pick`), so the split declares `back: { act: plugSet, args: { plugin: official.rsi, k: pick, v: $.home.listKey } }`; the engine places it in the detail head only when collapsed and picked (none side by side). `drill` is gone; the main page on a narrow window gets the same back.
- **Following the current conversation (alpha.17).** Every request sends `thread: host:currentThread.id` (the Host does not yet reread when the conversation changes; see below). The backend looks up the conversation's project. `follow()` (`src/views.ts`) decides what the page shows, for reads and writes alike: a choice made in this conversation, else the conversation's objective (an objective thread) or project (a project conversation), else the first real project. Choices are tagged with the conversation they were made in (`…#@thread`, built by the backend into `pickKey`, `choice`, `listKey`), so in another conversation they no longer apply and the page follows that one; a write acts on the shown project and pick.
- **Compound state (alpha.17).** `plugSet` takes `also`: changing project also clears `pick`; locate sets `selO` and switches `tab` to `version`.
- **New-objective navigation (alpha.17).** A write may return `acts`; `new` returns opening the new objective's thread, then the panel (`open { ref: plugin:official.rsi/rsi.panel }`), which follows that conversation to the objective.
- **Returned translation descriptors (alpha.17).** A returned `{ t, args }` (only those keys) is translated; `exp.next.hint` is returned as `rsi.exp.firstOf` text (empty when none). The `doingOf` / `doingAlso` notice stays composed in PDL.
- **Capability rename (alpha.17).** Group rows have a rename action: `dlg.rsiGroupRename` (field `arg: name`) calls the plugin's `groupRename` write.
- **Member option label (alpha.17).** Options read `rsi.memberOption` = `{0}（@{1}）`.
- **Demo projects (alpha.17).** Projects without a project directory are demo data and are labelled `（演示）` (`rsi.demoProject`); the page no longer opens on cartpole by default.
- **Switching conversations does not reread (Host).** `VM.plugin` (`packages/web/public/pdl-app/plugins.js`) builds a read's key only from its `@` values. A `host:` value is resolved when the read is sent but is not part of the key, so a new conversation does not start a read, and the page keeps the previous conversation until something else rereads it (a write, a selection). Fix in the Host: put `host:` values in the key too.
- **Old scripts after a Host upgrade (Host).** The first load after the upgrade ran the previous `pdl-app` scripts from the service worker, so the page did not follow the conversation; a reload fixed it.
- **`undefined` in the detail head while loading (Host).** While the detail is read for the first time, its head shows the text `undefined`.

Contract and loader details for integration:

- Each read uses its request name as a source alias (`home`, `objective`, `exp`, etc.), rather than using `v` for every request. The host's held-source key contains the alias and input, not the request name; reusing `v` makes different views share the first request's data. Repeated views of the same request still share its alias. Response bodies are unchanged.
- The GET request remains `policy`; its POST counterpart is named `setPolicy` locally, with `body.op: policy`. A single `requests` map cannot declare both methods under the same key.
- `life` and `prep` retain the prototype's `op` argument in their PDL action arguments, but serialize it as `body.action: "@op"`. `body.op` remains the request dispatcher (`life` / `prep`). The shared contract otherwise assigns both meanings to the same JSON key; backend dispatch must read the subordinate operation from `action`.
- All reads include the additional `selC: state.selC` query for the collection-version tree. Writes send the same page-state query so actions without an explicit objective can resolve the current selection. `record` additionally forwards opening input `type`, `objective`, `cycle`, and `id`; `cards` forwards `objective`; `doc` forwards `id`. These are dialog inputs, not new host-state interfaces. The backend README must include the extra `selC` state query.
- `readVerifiedConsole` reads every `.js` / `.css` file in `console/components`, then `PluginManagerService` overlays those source arrays on `pdl.yaml`. The YAML's `components: {js: [], css: []}` is the declaration shape; the served fragment receives the actual file contents. The browser executes strings as source code, so file paths do not belong in these arrays. The two drawings register only as `plugin:official.rsi/rsiLineage` and `plugin:official.rsi/rsiTrend`; no host action table is changed. YAML anchors are not used.

- **Dialog opener arguments (Job C).** The current public `A.dialog(d)` calls `dialog({ kind: d.kind, args: d })`. Opener arguments therefore put `kind`, `card`, `n`, `pick`, `id`, `title`, `value`, and `cats` at the same level; a nested `args` object would leave dialog `$.card` / `$.n` / `$.cats` unresolved. Submit requests still use their existing `okArgs` and field `arg`s.
- **New-objective project selection (Job C).** `home.projects[]` contains each project's `exp`; `home.pick.exp` describes only the selected objective. New-objective controls iterate the project list and match `id` to `home.projectId` with the engine's two reciprocal `gte` conditions, then select the experiment or ordinary dialog with `when: @exp` / `when: !@exp`. This also handles an empty project and the capabilities, library, and cards selections without adding a response field.

## Live walkthrough (rsi-demo-arith, alpha.21–28)

The demonstration project ran with `codex` preparing and `kimi` evaluating: initialization, cycle 1 (control, lower learning rate, no format reward; seeds 11 / 23), a step-4 rewrite of the guards, v2 (learning rate 3e-5, commit 07af917), cycle 2 (v1 0.155 vs v2 0.495, seeds 24 / 25; v2 candidate) and cycle 3 (confirmation, v1 0.075 vs v2 0.5075, seeds 26 / 27). v2 was adopted and the objective stopped at its target `accuracy ≥ 0.45`. Cycles 2 and 3 were started by the schedule inside the confirmed window. Problems found:

- **A metric decision asks the preparer for a version.** `expDecide` (`src/actions.ts`) sends every pick other than a candidate or `same` (direction, info, addVar, metric, goal) to the prepare member as a new-version request. Metrics are step 4 and belong to the evaluate member, so a `metric` pick should rewrite step 4 through that member, as the prep `agent` rewrite does.
- **No recourse when the evaluator cannot conclude (wake fixed, alpha.26).** Only the evaluate member can conclude, on the turn it claimed with `rsi.task`. In cycle 1 its session produced malformed tool arguments eleven times (recovered through the Host's session handoff, which the owner approved; the new session concluded on the first try); in cycle 3 its turn ended with an empty response. The evaluating notice now has 重新叫醒 (`evalAgain`), which sends the same evaluation request again. The evaluate member still cannot be changed after creation.
- **The probe does not run collect.** The executor probe runs only preflight, so step-4 metric ids that collect never reports are accepted; here the mismatch was caught by hand before cycle 1.
- **Guard thresholds are not compared with the baseline.** A guard the control fails on every seed makes every group ineligible. `arith-m-guard-signal ≥ 0.5` failed all six cycle-1 runs, including the group that beat the control by 0.44 accuracy, so nothing could become a candidate; `arith-m-guard-tail ≥ 0` can never veto. The walkthrough rewrote step 4 after the cycle-1 conclusion: signal 0.3 and tail 0.05 separate the two collapsed runs (accuracy 0, signal 0.22 / 0.227, tail ≈ 0) from the other four (signal ≥ 0.313, tail ≥ 0.2375).
- **A rewrite after the start did not hold the next cycle (fixed, alpha.22).** Rewriting a step moved only a `ready` objective back to preparing, so a running objective could start its next cycle on the old step while the member redid it. `runCycle` now requires the preparation to be settled (`prepSettled`, shared with `rsiExpReady`), and the notice says when a cycle waits for the evaluator's conclusion instead of showing the next window.
- **Redoing step 5 replaces the plan a decision made.** Every step-5 submission must carry `upcoming` and replaces `d.upcoming` (`src/init.ts`). After a version request or a candidate confirmation has set the next plan, a redo of step 5 (for example because step 4 was rewritten) overwrites it. The walkthrough avoids this by deciding only after the redone steps are confirmed; while a decision is pending, the notice shows the decision rather than the redo, which invites the other order.
- **Members were demo placeholders; directions showed a member id (fixed, alpha.24).** A new real objective copied the demo template's eight members and replaced only prepare and evaluate, so the page listed an executor, three analysts (分析甲 / 乙 / 丙 with made-up models), an iterator and a metrics member that never act. Real objectives now keep only the chosen members, with the name and model from the Host's member options (the tool context has no model, so a direction shows the model recorded at creation). Directions and members draw the identity component (`who`: avatar lead, name) instead of the stored id as text. The walkthrough's objective was created before this and still lists the placeholders.
- **No analysis members (FLOW §1.4, §2 members).** FLOW has one evaluator (metrics, predictions) and several analysts (different models, directions signed side by side; the plugin sends the same report to all of them and says whether they agree). The plugin has only the evaluator, who writes every direction. Choosing analysts needs a member picker: FLOW asks only prepare and evaluate at creation and takes analysts from project defaults, changed later in 成员; choosing them in the creation dialog needs the Host dialog's option fields to accept `memberPick` (multi, avatar lead) — `overlays.js` renders a field as `sel(id, options, value, { change })` without `multi` or a lead.
