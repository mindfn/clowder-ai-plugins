## Console

- **Panel width.** `rsi.panel` keeps the narrow list/detail levels, with the standard drill back action setting `state.list` to `true`. The main page retains the full split. `S.panelWide` is private host state and cannot select a plugin layout.
- **Panel selection and compound state.** Host `A.plugSet` writes one key; it has no equivalent of prototype `SET_AFTER['s.rsiPick']` or the `s.rsiTab|s.rsiSelO` multi-set. On the panel list, choose an item and use “View selection” to set `list: false`. Locate sets `selO` from the existing `version|…` value; it cannot also switch to the Versions tab. Changing project sets `project` without the prototype's simultaneous pick reset. The backend's `go` / `goVersion` responses have the same one-follow-up-action limit.
- **Following the current thread.** `bindPluginRequests` exposes `host:currentThread` as `VM.chatHeader`. Its request-value resolver only handles `state.*`, `@input` paths, and the literal `host.origin`; it cannot bind a host source into a read query. The prototype's automatic thread-to-project/objective selection and panel following are therefore unavailable. No private thread state or invented request binding is used.
- **New-objective member choices (resolved in Job C).** Opening views read `members: host:members` and pass `defaultCatOptions` as `cats`. `dlg.rsiNewExp` initializes its options from `$.cats`, with values from `id`, labels from `name`, and the prototype defaults `opus` / `codex`. Its unsupported dialog `sources`, loading, and error declarations are removed. Record/document headers still use the title supplied in their opening arguments; their bodies use declared read requests.
- **Member option label format (Job C).** The requested `<name>（@<id>）` label needs a translation template or a preformatted option label. Host `defaultCatOptions` supplies only `id`, `name`, and `model`; `pv` cannot concatenate bindings in an option row, and the existing RSI zh/en packs contain no matching template. This job can only edit PDL and this Console section, so the dialog displays `name` and posts `id`. Inline PDL translations would be overwritten by the host loader's `console/i18n` packs.
- **Returned translation descriptors.** A `{t,args}` object written directly in PDL is translated. A descriptor returned by a request and reached through a binding such as `$.exp.next.hint` is returned unchanged by `pv`; `pvText` / `tc` then stringify it instead of recursively translating it. The prototype's `exp.next.hint` and composed `exp.next.by` messages need a host data-localization mechanism or a revised response shape. The console keeps the shared response contract and does not pretranslate backend data.
- **New-objective navigation.** A write can return one public follow-up action. `new` can open the new objective's thread, but it cannot also open `rsi.panel` as the prototype does. The console adds the panel entry; automatic opening still needs a second host action.
- **Capability rename.** The prototype's group rename uses private `rename` / `ENT.rsiGroup`. `rename` is absent from `PLUGIN_PUBLIC.acts`, and the shared write contract declares no group-rename action. The capability rows omit that operation so the host will accept the fragment.

Contract and loader details for integration:

- Each read uses its request name as a source alias (`home`, `objective`, `exp`, etc.), rather than using `v` for every request. The host's held-source key contains the alias and input, not the request name; reusing `v` makes different views share the first request's data. Repeated views of the same request still share its alias. Response bodies are unchanged.
- The GET request remains `policy`; its POST counterpart is named `setPolicy` locally, with `body.op: policy`. A single `requests` map cannot declare both methods under the same key.
- `life` and `prep` retain the prototype's `op` argument in their PDL action arguments, but serialize it as `body.action: "@op"`. `body.op` remains the request dispatcher (`life` / `prep`). The shared contract otherwise assigns both meanings to the same JSON key; backend dispatch must read the subordinate operation from `action`.
- All reads include the additional `selC: state.selC` query for the collection-version tree. Writes send the same page-state query so actions without an explicit objective can resolve the current selection. `record` additionally forwards opening input `type`, `objective`, `cycle`, and `id`; `cards` forwards `objective`; `doc` forwards `id`. These are dialog inputs, not new host-state interfaces. The backend README must include the extra `selC` state query.
- `readVerifiedConsole` reads every `.js` / `.css` file in `console/components`, then `PluginManagerService` overlays those source arrays on `pdl.yaml`. The YAML's `components: {js: [], css: []}` is the declaration shape; the served fragment receives the actual file contents. The browser executes strings as source code, so file paths do not belong in these arrays. The two drawings register only as `plugin:official.rsi/rsiLineage` and `plugin:official.rsi/rsiTrend`; no host action table is changed. YAML anchors are not used.

- **Dialog opener arguments (Job C).** The current public `A.dialog(d)` calls `dialog({ kind: d.kind, args: d })`. Opener arguments therefore put `kind`, `card`, `n`, `pick`, `id`, `title`, `value`, and `cats` at the same level; a nested `args` object would leave dialog `$.card` / `$.n` / `$.cats` unresolved. Submit requests still use their existing `okArgs` and field `arg`s.
- **New-objective project selection (Job C).** `home.projects[]` contains each project's `exp`; `home.pick.exp` describes only the selected objective. New-objective controls iterate the project list and match `id` to `home.projectId` with the engine's two reciprocal `gte` conditions, then select the experiment or ordinary dialog with `when: @exp` / `when: !@exp`. This also handles an empty project and the capabilities, library, and cards selections without adding a response field.

## Backend

- **Agent submissions and execution events — phase 2.** Replace the timed reply in prototype `rsiExpStep`, the prep `agent` route's `setTimeout`, and its opinion-rewrite wrapper with plugin MCP handlers calling `submitInitStep`. `rsiExpKick` already records deterministic `exec` IDs and dependency revisions; it emits dispatch entries without fake responses. Bind thread `execution_status` events to `recordInitExecution`, then persist through the same owner-key CAS. Agents must explicitly submit content, executor probe results, docs, and the upcoming baseline plan. Seeded PD's in-progress preparation still needs real member bindings and submissions.
- **Thread creation, cards, and mentions — phase 2.** Replace prototype `rsiExpNew`, `rsiExpMsg`, `rsiExpSync`, `rsiExpChanged`, and `A.rsiNew`'s host side effects with an outbox consumer. `createThread` entries precede goal cards and member dispatches; `bindObjectiveThread` attaches an actual returned thread ID. New objectives currently have no thread ID and return `{ ok: true }`, never a fabricated `thread` follow-up. Once creation can return a real ID, return `{ ok: true, act: 'thread', args: { id } }`. The additional `openPanel('rsi.panel')` action and prototype `rsi:changed` thread refresh need separate host support because the response permits one follow-up action. Interactive card decisions currently use the HTTP `expDecide` write; replace the prototype `/api/messages/:id/block-state` wrapper with an authenticated outbox-card decision callback.
- **Actual nightly work — phase 2.** Replace prototype `rsiExpNight`'s interval, the rounds `decide` route's scripted PR merges/automatic next-night timeout, and lifecycle-generated evaluation results with schedule/run/executor outbox consumers. Phase 1 stores decisions and planned cycles and records start/retry/pause/resume requests; it produces no agent conclusions, PR merges, or measured runs. Passive project analysis/preparation (the project-objectives POST timers) and passive card reevaluation also require agent submissions; their requests are retained in the outbox. Wire execution-capability registration/probes and disable/enable dispatch to replace prototype `rsiExpStep`'s `s.exec` branch and lifecycle capability toggles.
- **Current-thread data — phase 2 console hook.** Prototype `VM.rsiHome` reads `S.thread` through `/api/rsi/threads/:threadId`. The backend accepts a `thread` query and returns the associated project/pick. The console must supply that host thread ID and use the resolved selection for subsequent child requests; the backend does not invent a host binding or store console navigation state.
- **Members and host-only labels — phase 2 console hook.** Replace `/api/cats` reads in `VM.rsiNewExp` and `rsiPolicyOf` with console member data. New writes already accept/store `prepare` and `evaluate` IDs, and dispatch by ID. `newExp.cats` is empty; known stored IDs can appear as policy labels. Passive trace fixtures use stored/project-policy member IDs and stored thread IDs for labels, replacing the prototype trace route's `FX.cats` / `FX.threads` lookups. The console must resolve actual display names, model labels, and thread titles.
- **Returned translations — console/host hook.** Prototype `tc` calls in `VM.rsiExp` return `{t,args}` descriptors here. `next.by` is an array of `rsi.exp.doingOf` descriptors because the prototype joins translated strings; joining descriptor objects would destroy them. The current console engine does not recursively localize descriptors obtained through request bindings, as verified by the console job. It needs returned-data localization and composition support; plain VM strings remain unchanged.
- **Single follow-up navigation — console hook.** Prototype `A.rsiGo` sets pick, tab, and object selection; `A.rsiGoVersion` sets tab and object selection. Their POST equivalents return only `plugSet(pick)` or `plugSet(selO)`. The console needs a public compound-state mechanism to also reset/switch the tab and clear the old selection. Prototype `A.rsiReeval` also reopens the previous cards dialog after submitting; that second navigation is not representable in one response.
- **Request shape clarifications.** The prototype's `A.rsiLife` and `A.rsiPrep` already use an `op` argument; serializing that beside the dispatcher would overwrite `body.op`. The console and backend use `body.action` for this subordinate operation. All writes accept the read page-state query to replace captured `S.rsiProject` / `S.rsiPick`; `body.objective` can identify a target directly. Document dialogs accept their opening `id` query, and policy writes accept the console's `v`. These are request data, not new host interfaces.
- **Unmounted VM calls.** Prototype `VM.rsiObjective` assumes passive cycle data once `running` exists and throws on an experimental detail; the backend routes that otherwise unmounted request to the experimental VM so all named reads remain usable. Missing objective/dialog data returns JSON null. The actual experimental console still mounts `VM.rsiExp` as the prototype does.
